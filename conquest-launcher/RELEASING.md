# Current release workflow

## Production source protection (0.6.8+)

`npm run build` and `npm run build:dir` invoke the `beforePack` hook automatically. It generates `.production` from the readable development sources using pinned esbuild, with separate minified CommonJS main/preload bundles and a shared-scope renderer IIFE. Renderer-only javascript-obfuscator uses conservative identifier/string-array transforms; properties, IPC names and exposed APIs are not renamed. No eval, anti-debugging, self-defence, control-flow flattening or source maps are enabled. Development `npm start` and preview still use the original source.

Only generated `runtime/a.cjs`, `runtime/b.cjs`, `public/c.js`, HTML, CSS, static assets, public configuration, package metadata and external production dependencies enter app.asar. The addon catalog remains the existing separate resource; no client files or addons are transformed. Build-only packages, tests, scripts, source trees and all `.map` files are excluded from player packaging. Third-party dependency code and licenses remain intact.

Electron Builder disables RunAsNode, NodeOptionsEnvironmentVariable and NodeCliInspectArguments, and enables EmbeddedAsarIntegrityValidation and OnlyLoadAppFromAsar. The afterSign hook verifies the archive allowlist, generated bytes, source-map absence, fuse wire and embedded Windows ASAR header hash before generating installer ownership hashes. Do not edit the ASAR or EXE afterward. Use `node tools/protected-package.cjs` to inspect the final unpacked output.

Run `npm test` once for final validation. Run the desktop smoke with `COA_PRODUCTION_TEST=1` to exercise the exact generated bundles and unchanged preload bridge using disposable client files and mocked services. It uses the development Electron binary so test automation can inspect it; the shipping EXE's fuses and integrity are checked separately after packaging. There are no test switches in the shipping bundles. `PLAYWRIGHT_MODULE` may point to the installed Playwright package.

The app ID, executable name, update feed, NSIS integration and settings identity remain unchanged. Publish the new version through the existing workflow only after approval; packaging itself never deploys. Existing installers can upgrade without wiping the install folder. The preservation policy may retain older readable ASARs in historical backups; this pipeline protects new payloads and does not erase previously distributed copies. Minification/obfuscation raises reverse-engineering effort but cannot make client-side JavaScript unrecoverable.

Implementation references: [esbuild API](https://esbuild.github.io/api/), [javascript-obfuscator](https://github.com/javascript-obfuscator/javascript-obfuscator/tree/4.1.1), [Electron fuses](https://www.electronjs.org/docs/latest/tutorial/fuses), [Electron Builder fuses](https://www.electron.build/docs/tutorials/adding-electron-fuses/). Build behavior was also checked against installed electron-builder 26.15.3 and Electron 44.3.0 tooling.

Client compatibility is opt-in: append `MINIMUM_LAUNCHER_VERSION` (stable `major.minor.patch`) to the `publish-client.cjs MASTER_FOLDER PUBLISHED_FOLDER RELEASE_NAME` command only when the release requires it. The publisher writes `minimumLauncherVersion`; supporting launchers reject incompatible releases before object downloads and show update instructions. Omit it for ordinary content updates. The release menu continues publishing unrestricted releases.

This gate is supported starting in launcher 0.6.7. Older binaries cannot be made to honor a new manifest field retroactively. Distribute the supporting launcher before relying on this field; a genuinely incompatible file format must also change the manifest schema so older launchers reject it. No minimum has been imposed on the existing published client.

In the source project, follow `../BUILD_AND_RELEASE.md` for building and preparing the handover ZIP, and `../PRODUCTION_DEPLOYMENT.md` for host installation and updates. When this file is copied into `dist/release-tools`, use the guides supplied with the handover instead; source-relative paths no longer apply. Full compilation, installer generation, VPS packaging and publishing are separate manual steps.

Increment package.json/package-lock.json version before a changed release. `npm.cmd run build` creates NSIS artifacts and `dist/launcher-release`; it does not compile the backend. Publish current Linux backend output as described in the build guide before `npm.cmd run package:vps`, which collects a new validated deployment archive. Use the newly generated archive, not a historical bundle. Players receive only the installer EXE. The host receives the archive plus the complete production game client for first installation; private settings are exchanged separately.

On the VPS, use section 12 of `PRODUCTION_DEPLOYMENT.md` to select launcher-only, game-only, backend/tools or combined updates. Packaging alone does not publish anything. The host publishes the full launcher release folder for self-updates, and validates/publishes the private master with a unique client release name for game updates. Players click UPDATE before game downloads begin and choose Restart & Update for launcher installation.

## Launcher self-update (GitHub)

See `../docs/RELEASING-THE-LAUNCHER.md`: every launcher release needs the installer, its `.blockmap` and `latest.yml` (`dist/github-release` after `npm run build`), published with `gh release create vX.Y.Z ... --latest`.
